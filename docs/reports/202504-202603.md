# Progress report April 2025 - March 2026

## Summary

- A 4 node TETREs network is running
- We have documentation for deploying Netbird in a varietry of configurations
- Inter-TRE connections to a PostgrSQL server and Flower AI SuperLink node has been demonstrated, with different partners running the Mesh network management hub, the PostgreSQL server, and the Flower AI SuperLink.

- Swansea University: Installed hardware for a new on-premises TRE testbed, and evaluated technologies for a mesh network architecture, eventually recommending Netbird
- University of Dundee: An early version of K8TRE (still in development) was deployed in AWS and connected to TETREs. Connections to PostgreSQL validated, and a Flower AI SuperLink (the equivalent of a central hub/server) was also deployed and configured to allow incoming connections from other TETREs nodes
- University of Edinburgh: Deployed the Netbird Managment node for TETREs on OpenStack, configured all mesh networking policies, ran a PostgreSQL server, and also started looking at additional options for federated analysis such as [Federated Learning Interoperability Platform](https://londonaicentreflip.readthedocs.io/en/latest/index.html)
- Lancaster University / Lancashire and South Cumbria NHS Foundation Trust: A modified version of K8TRE was deployed in Microsoft Azure and connected to TETREs, and also looked at independently deploying a Netbird management node
- The Alan Turing Institute: Connected a test deployment of the [Turing Data Safe Haven](https://github.com/alan-turing-institute/data-safe-haven) to TETREs, and validated connecting to PostgreSQL and Flower AI

## Netbird setup including infrastructure-as-code

### Edinburgh: Netbird Management node

This was largely completed by following Netbird's self-hosting setup guide and other documentation: https://docs.netbird.io/selfhosted/selfhosted-quickstart.

1. Created a VM (Ubuntu 24.04, 4CPU, 8GB RAM) in our OpenStack cluster and assigned it an external static IP from our pool. Installed Docker
2. Registered `<management-host>` and created a DNS record pointing it at the external IP
3. Added firewall rules allowing external traffic to reach the VM:
    - 80/tcp (LetsEncrypt challenge)
    - 443/tcp (Netbird Management UI)
    - 3478/udp (STUN)
4. Ran the Netbird installation script, selecting the built-in Caddy proxy
5. Opened Netbird dashboard, registered an admin user, and created the `<management-net>` virtual network
6. Created a setup key

### Edinburgh: Netbird agent

For simplicity, the agent was installed on the same VM as the management node. Installation proceeded following this guide: https://docs.netbird.io/get-started/install/linux.

1. Ran the Netbird installation script
2. Connected to the management node with `netbird up --setup-key <SETUP KEY> --management-url <URL>`
3. Checked with `netbird status` and `ip addr show wt0`

### Dundee: Netbird agent

Everything is running on Kubernetes

This is currently deployed on AWS EKS as a Helm chart with ArgoCD (full infrastructure-as-code), and assumes Cilium CRDs for Network Policies are installed.
See this repository: https://github.com/hic-infra/k8tre-flowerai/tree/3fa610ceba67e4ff3d128fd619fd4d8b9e2792d9

The Netbird client is run as a sidecar alongside Haproxy, using the official Netbird container image.
The environment variables: `NB_MANAGEMENT_URL` and `NB_SETUP_KEY` ensure this is portable to other deployments.

HAProxy listens on some ports and forwards requests to a service (in this case FlowerAI SuperLink node).
The Netbird client transparently makes HAProxy and the services it is fronting available on the Netbird network.

### Lancashire: Netbird agent

This was deployed on Azure using the [NetBird Kubernetes Operator](https://github.com/netbirdio/kubernetes-operator/pkgs/container/helm-charts%2Fnetbird-operator) deployed into the netbird namespace via ArgoCD.

The operator is responsible for;

- Watching the annotation `netbird.io/setup-key` on pods
- Auto-injects a NetBird sidecar container at admission time (via a mutating webhook)
- Reads the referenced NBSetupKey CRD to determine which NetBird management server (hub) to connect to

The only configuration is;

- ExternalSecret and NBSetupKey CRD in the corresponding namespace (via ArgoCD)
- Add annotation to the pod or deployment

The operator handles the rest to connect to the mesh network.

#### NBSetupKey CRD

This CRD is created per namespace, and it registers the namespace with the management URL (eg Edinburgh Netbird management server)

```yaml
apiVersion: netbird.io/v1
kind: NBSetupKey
metadata:
    name: cluster-setup-key
    namespace: netbird-test-sidecar
spec:
    managementURL: <management-host>
    secretKeyRef:
        name: netbird-secret
        key: NB_SETUP_KEY
```

#### Pod Annotation

The operator's webhook intercepts the pod at creation and automatically injects the NetBird sidecar. It will then help to establish the WireGuard tunnel connection

```yaml
apiVersion: v1
kind: Pod
metadata:
    name: psql-test
    namespace: netbird-test-sidecar
    annotations:
        netbird.io/setup-key: cluster-setup-key
spec:
    containers:
        - name: psql
          image: docker.io/alpine/psql
          command:
              - sh
              - -c
              - "sleep 15 && psql -h <sqlserver>.<management-net> -p 5433 -U test -d tetres -c 'SELECT * FROM hello_world'"
          env:
              - name: PGPASSWORD
                value: test
    restartPolicy: Never
```

#### Operator Configuration

```yaml
# Management hub
managementURL: <management-host>

# API key allows the operator to manage peers and policies on the hub
netbirdAPI:
    keyFromSecret:
        name: netbird-secret
        key: NB_API_KEY

# This will intercepts pod creation to inject sidecars
webhook:
    enableCertManager: true
    failurePolicy: Fail

# It handles inbound mesh traffic to exposed services
ingress:
    enabled: true
    kubernetesAPI:
        enabled: true
    namespacedNetworks: false
    allowAutomaticPolicyCreation: true
    router:
        enabled: true
        replicas: 1
```

#### How the Sidecar Works

In Kubernetes, every container inside a pod shares the same network namespace. This means they can see the same network interfaces and the same routing table.

When the NetBird sidecar starts it:

- Connects to `<management-host>` and authenticates using the `NB_SETUP_KEY`
- Receives the list of peers it is allowed to reach
- Creates a WireGuard interface `wt0` directly in the pod's shared network namespace
- Injects routes so that traffic to NetBird IP ranges is sent through `wt0`
- Starts a local DNS resolver that resolves `*.<management-net>` → NetBird IPs

Example of making a query to a resource over Netbird:

1. psql issues a DNS query

    - `psql -h <sqlserver>.<management-net> -p 5433`

2. NetBird sidecar's DNS resolver answers

    - Resolves `<sqlserver>.<management-net>` → `100.xx.xx.xx`
    - this will be the NetBird mesh IP of the Edinburgh database host

3. Kernel routing selects the wt0 interface

    - psql opens TCP connection to `100.xx.xx.xx:5433`
    - Packet is then handed to the WireGuard interface

4. WireGuard encrypts and sends

    - `wt0` encrypts the packet using the Edinburgh peer's WireGuard public key
    - Sends it as a UDP packet over `eth0` → `internet` → <management-host>`

5. EIDF NetBird hub forwards to the peer

    - Mostly the two peers will establish a direct WireGuard tunnel

6. Edinburgh PostgreSQL receives the query

    - Decrypts the packet, executes: `SELECT * FROM hello_world`
    - Here, the response follows the same path in reverse

7. psql container receives the response

    - psql just sees a normal TCP connection to port `5433`.
