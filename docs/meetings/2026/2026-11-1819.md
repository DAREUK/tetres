## DIRECTOR technical deep dive

DIRECTOR: suite of 5 products

Collabora office included

Docusign

DIRECTOR MESH

- command \& control of Mesh network
- "Interim" product that will be succeeded by DIRECTOR
- Built around Netbird, managed through API
- But Netbird could be replaced, DIRECTOR-mesh API remains unchanged
- [https://github.com/SwanseaUniversityMedical/Director-MESH](https://github.com/SwanseaUniversityMedical/Director-MESH)

"Collaboration":

- Group of organisations
- Contract to do something together

Start from Consortium agreement

- Consortium then goes to a Netbird provider
- Netbird: "owned" by consortium in the sense that consortium has a contractual relationship

How many collabs will we have in the UK?

- More than one since not everyone agrees
- Collab: either focussed on a program of work, or a group of organisations that are forming a shared facility
- Former: collaboration agreement (time limited). Latter: a partnership agreement (can be indefinite).
- Forming a new collab should be straightforward, no big deal, avoid being boxed in, easily setup a new collab instead of forcing agreement with an existing group
- What's the baseline? Minimum risk appetite?

Multiproject infrastructure?

- E.g. don't want to install 5STES 20 times on the same infrastructure
- Need to decide where to deploy it
- Need to decide which node is the "director"
- Other nodes have a director agent that contacts director
    - Contacted over mesh
    - Director then deploys everything
- E.g.
    - FlowerAI: Decide which node is SuperLink and which are SuperNodes. Egress must be added on.
    - 5STES: Submission node: Egress on each worker node
    - Those nodes take on the "lead" role
    - One front door per deployed software, and not the same as main director node

Everything based around K8S

- Either your own
- Otherwise Director-zero deploys K8S for you
- Prob makes sense to deploy a dedicated K8S for this, but up to institution
- Director then deploys k8s apps
- Layer 1: ArgoCD
- Layer 2: admin layer
- Layer 3+: Applications

Consortium agrees to deploy plane for a purpose, contains applications

- Not every node in a consortium needs to be part of a plane
- Layers are "fabric" of federation
- Plane may not be project specific, could be domain specific for a group of projects
- A Plane could be only one TRE, e.g. if you want to deploy Carrot for a single TRE. Director can manage it instead of TRE, especially if director is already deployed
- Plane is also a security boundary, planes shouldn't talk to each other
- E.g. Plane could be 5STES covering all projects
    - A project is deployed in that plane
- Plane: A K8s namespace

Director: provides UI

- e.g. flowerAI: Director presents a FlowerAI specific interface to select who the SuperLink and SuperNodes are
    - UI needs to know architecture (one SuperLink, multiple SuperNodes, SuperLink can be a SuperNode)
- JSON payload sent to Director agents
    - Node approves (or rejects) proposed configuration
    - If everyone agrees, deployed, otherwise reconfigure
- If necessary could also construct JSON payload outwith UI
- Payload also tells a node what's happening with other nodes to provide full context
- A lot of trust placed in Director, has responsibility for understanding all products
    - Other nodes should pay attention.....but may not

JSON payload + Mesh

- Director owns Mesh, so creates endpoints depending on product
- Within mesh: need to configure DNS (e.g. SuperNode needs DNS to connect to SuperLink)
- Endpoints: Haproxy pods with Netbird agent
- UI: if approved UI creates ArgoCD Application YAML with Kustomise, YAML, and Helm, in Gitea

Central services:

- Global Vault alongside Director
    - May use cloud native secrets services instead
    - Director fills Vault
- Keycloak

Helm chart: TRE could pull from public repos, or Director can configure internal repo/mirror

Versioning?

- UI -> Update Gitea -> Deployed by ArgoCD
- Still need to be approved by TRE
- If TRE doesn't agree: reject member?
- Collaboration agreement needs to allow updating versions

If agreement changes: new contract, so be careful what goes into it

But you're trusted Director to only make infrastructure changes that comply with the agreement

- But changes should be auditable/visible. All CICD, so pull requests can be visible
- In practice, Director role is most likely an established TRE to provide continuity

User access:

- Workspace has access to FlowerAI SuperLink

Node can be in multiple consortia

- multiple Director agents, probably multiple K8s clusters

Mapping local pods to local resources e.g. data

- Currently only 5STES carries identities through
- FlowerAI doesn't, so effectively delegate trust to SuperLink

New TREs: wouldn't be trusted to be Director, or SuperLink, until they've proven themselves

Can we have a specification for how a TRE qualifies to be a DIRECTOR?

- SATRE is a start
- Do other TREs trust you?

AIRR-BRIDGE

- Would it be another node, or would it cross the mesh?
- Recently changed to use Netbird to connect TRE to FRIDGE
- At the moment FRIDGE assumes it's only connected to one TRE so not designed to auth other users
- In principle could connect FRIDGE directly to MESH as a TRE node
    - potentially very valuable
    - has a set of capabilities (GPUs), disallow other generic capabilities
    - but not at the moment since assumes if you can connect to FRIDGE you're allowed to send jobs
- Or FRIDGE can be connected directly to TRE as at present, or connected to 5STES
- Director agent: somehow running in (or attached to) the HPC facility

Auth: application specific

- Pushed down to TRE
- Definitely needs to be auditable
- 5STES: agent runs workload, ephemeral credentials for connecting to all services. Ephemeral credentials can be linked to the original user. Works because it's written by TRE community
- Vs FlowerAI: no passthrough credentials, designed by another community
- Mesh restricts what can connect to what

Applications:

- May have optional dependencies, e.g. databases
- Director agent: configure whether it deploys database or uses an existing one
- Sharing infrastructure? 3 DB servers vs 1 DB server with 3 databases
- Director agent needs to wire everything up, DB connection string is a K8S secret
- Unstructured data: S3 bucket, with permissions + credentials
- Own DB: create service account to worker node, inherently restricts what worker can access

When are things deleted?

- Director sends a delete message
- If approved, deleted from ArgoCD
    - but might want option to not delete databases that were created by Director

Inter-plane communication

- Actually be allowed
- Service planes
- Common plane: shared services
    - e.g. only want a single egress
    - site Keycloak
    - site DB

Director WFS

- Workflow service
- All-in-one single-node TES deployment with KIND

Tech Support?

- Who's responsible?
    - First line support: The TRE a user is using, e.g. whoever runs the 5STES submissions node
        - Second line: Escalate to Director
- Should Director monitor remote K8S clusters?
- Prometheus + Grafana is a good start, see why a cluster is failing
    - If run over mesh, visible to all
- Who sees director dashboard?
    - Transparency: could be everyone?
    - 5STES: takes view that everything is visible since it's making connections outside TRE, possibly embargoed
- TRE private, TRE public, public public
- Freedom of information already has to be considered
